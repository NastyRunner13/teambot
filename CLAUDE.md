# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

TeamBot is a self-hosted workspace (for one person, or a small team with sign-in turned on) where named AI agents (any OpenRouter model per agent) each get their own isolated Docker "computer" and collaborate with humans and each other in chats, group chats and (among agents) a task board. Every tool call passes a policy gate. P0 and P1 are complete; the roadmap (P2 next) and the P1 progress table live in `docs/FEATURE_MAP.md` (check its priorities before proposing new features).

## Commands

pnpm 10 monorepo, Node ≥ 22.13 (the server uses the built-in `node:sqlite`). Docker is needed only for real agent computers.

```bash
pnpm install
pnpm dev                 # server :8787 (tsx watch) + Vite :5173 with /api proxied; open :5173
pnpm build               # builds apps/web only; the server has no build step (runs TS via tsx)
pnpm start               # server on :8787, serves apps/web/dist if it exists
pnpm test                # vitest in apps/server (the only package with tests)
pnpm typecheck           # tsc --noEmit in server, web and computerd
pnpm computer:build      # docker build of the agent computer image (computer/)

# single test file / single test
pnpm --filter @teambot/server exec vitest run test/policy.test.ts
pnpm --filter @teambot/server exec vitest run test/runtime.test.ts -t "answers a DM"

# end-to-end against a real container (needs Docker + the built image)
TEAMBOT_DOCKER_TESTS=1 pnpm --filter @teambot/server test
```

There is no linter or formatter configured. Config comes from env vars, and `.env` at the repo root is loaded by `apps/server/src/config.ts`, which walks up to the folder containing `pnpm-workspace.yaml`; variables already set in the environment win over `.env`. See `.env.example`. `OPENROUTER_API_KEY` is required for agents to think (or set `TEAMBOT_OFFLINE_MODELS=1` for a free echo model when trying the UI). Runtime data lives in `./data`: the SQLite DB, `master.key`, `shared/`, `skills/<name>/SKILL.md` and `memory/` (`team.md`, `agents/<Name>.md`).

`.claude/launch.json` has a `teambot-verify` configuration: a server on :8788 with its own data folder and offline models, serving `apps/web/dist` (run `pnpm build` after UI changes). Use it to check UI work without touching the real workspace or spending credits.

## Architecture

Packages: `apps/server` (Fastify + runtime), `apps/web` (React 19 + Vite + zustand + wouter), `packages/shared` (domain types, consumed as raw TS source with no build), `computer/` (agent container image + `computerd`).

### Server composition (`apps/server/src/app.ts`)
`createApp(cfg, overrides)` wires everything into one `App` object that is passed to every service (`store, bus, vault, policy, models, computers, mcp, tools, workspace, runtime, cron, budgets, skills, memory, proactive, lifecycle, telegram, slack, telemetry, egress, snapshots, triggers, helpers, auth`). Tests swap `models`, `computers` and the outside APIs (Telegram, Slack, mail, calendar, OTLP) for fakes through `overrides`. Server imports use NodeNext ESM, so relative imports need the `.js` extension. Web uses Bundler resolution, so it doesn't.

### State, events and the UI
- `store.ts`: all persistence on synchronous `node:sqlite`. Schema changes are **appended** to the `MIGRATIONS` array (versioned by index in `meta.schema_version`). Never edit an existing entry. Node 22's SQLite has no FTS5, so search uses `LIKE`.
- `bus.ts`: `bus.emit(type, scope, data)` appends to the `events` table, which serves as both the **audit log** and every run's work log (the notes in chats and the panel's full log), then fans out to WebSocket clients on `/api/ws`. Spend is computed from events too: every model call emits one of `COST_EVENTS` (`runtime/budget.ts`) with `costUsd`/`inputTokens`/`outputTokens`, so a new kind of model call must emit cost the same way or budgets won't see it.
- Web: `apps/web/src/store.ts` loads `/api/bootstrap` once, then applies live events by `type` (e.g. `agent.*` events carrying `data.agent` are upserted). A server-side state change only shows up live if it emits an event the web store handles. The channel view holds top-level messages (with `replyCount`); thread replies live in `threads[rootId]`. The UI is a chat app (see `design.md`): the sidebar lists conversations from `lastMessages`, a chat shows work notes from `runSummaries` (`/api/runs?ids=`), and the right panel's pages (`panel.view`) are scoped to the path they were opened on (`panel.at`).

### Work routing (`workspace.ts`)
Posting a message is how work gets routed. `@mentions`, DMs to an agent, human replies in a thread an agent is part of, a channel's `leadAgentId` (for human messages that mention nobody), task assignments and hand-offs, routines (`runtime/cron.ts` fires them; triggers are cron, webhook, email/calendar polled by `runtime/triggers.ts`, and Slack channel messages from `bridges/slack.ts`) and follow-ups on quiet tasks (`runtime/proactive.ts`) all add rows to the agent's **inbox**. A DM is between the two members it was opened with, forever: posting joins only group channels, and in a DM with an agent only that agent gets the message (a mention routes into a DM only between people). The web finds a person's chat with an agent by exactly those two members, so a DM that gained one would vanish from the UI. Telegram and Slack DMs come in through `bridges/` as the owner's messages. Helpers (`runtime/helpers.ts`, `spawn_helpers`) are agents with `parentId` that get one task each, share the parent's budget and are removed when their task closes. Each item carries a `depth` (agent-to-agent hops since a human), an `initiator` (human/agent/schedule/event), an optional `threadId` and a `readOnly` flag. If depth exceeds `TEAMBOT_MAX_AGENT_DEPTH`, the loop guard drops the item. Attachments are paths in `/shared` (`shared-files.ts`), validated on the server where they really lead: agents can create links in `/shared`, so reads go through `openSharedFile`/`realSharedPath` and uploads never follow a link.

### Runtime (`runtime/runtime.ts`)
- **Scheduling:** `poke()` and a 3 s timer dispatch at most one active run per agent, capped by `maxConcurrentRuns`. An agent over budget (`runtime/budget.ts`) is skipped; its work waits. A run turns inbox items into a user message. Inbox items for the same conversation (channel, thread and read-only flag) that arrive mid-run are folded into the same run; anything else waits for its own run (`belongsTo`), so a DM is never answered in a channel. Consuming input, saving the transcript and updating the run happen in one `store.tx`.
- **Each step:** the budget is checked (over budget → the run goes back to `queued` with a message), the system prompt is rebuilt from scratch (`runtime/prompt.ts`: roster, open tasks, skills, memory, secret names), then the model is called and the transcript is persisted. Long transcripts are summarized by the utility model (`runtime/compaction.ts`). A final assistant message with no tool calls is posted to the run's channel (and thread) automatically. The reply `[silent]` suppresses it. Read-only runs are offered only tools for which `usableReadOnly(tool)` holds (risk `read`, or `readOnlyOk: true`; never set it on a tool that changes memory, tasks or agents). Messages a read-only run sends route work to other agents as read-only too.
- **Durability:** state lives in the DB (transcript + `tool.started`/`tool.finished` events), not in memory. On restart, `recover()` re-queues `running` runs. A tool that started gets an explicit result instead of being re-run: "Interrupted" if it never finished, or the `tool.finished` preview if it finished before its result reached the transcript. It is **never silently re-run**. Pausing or cancelling a run also calls `computers.cancelWork` (computerd's `/cancel`) and waits for it, so no command keeps running on the computer. Keep this invariant when touching the loop.
- **Gateway (`handleCall`):** zod-validate args → collect `facts` (for browser tools, the target element label, field type and domain, fetched from the computer) → `policy.evaluate` → for `review`, ask the reviewer model (`runtime/reviewer.ts`; any failure means `ask`) → for `ask`/`handoff`, create an Approval and return `waiting_approval`/`waiting_human` (the run resumes when `resolveApproval` re-queues it) → `vault.resolve` substitutes `{{secret:NAME}}` → execute → `vault.redact` the output → truncate → wrap in `<untrusted_content>` if the tool is `untrusted` → emit events. Secret values never enter prompts or transcripts (screenshots from an action that used a secret are withheld; values under 4 characters are refused), but an agent with a shell can still deliberately reveal one it may use.
- Pause, cancel, takeover and hand-back work by aborting the run's `AbortController` with a reason.
- **Computers over time** (`runtime/lifecycle.ts`): tools get their computer through `lifecycle.ready(agent)`, which starts it on the agent's image and runs its setup script once per script version (marker in `~/.teambot/setup.sha`). A sweep stops computers idle for `TEAMBOT_COMPUTER_IDLE_MINUTES`, never while the agent has an active run, a takeover or a live viewer.

### Tools (`tools/`)
Tools are `defineTool({ name, description, schema (zod), risk, untrusted?, facts?, summarize?, execute })`. `risk` (`internal | read | write | external`) selects the policy default; `untrusted: true` tags the output as outside content. Built-ins are `workspace-tools.ts` (messages with attachments, tasks, `ask_for_approval`/takeover requests via `FORCED_APPROVAL_TOOLS`), `knowledge-tools.ts` (`use_skill`, `remember`/`forget`, `search_history`), `helper-tools.ts` (`spawn_helpers`, and `create_agent` for permanent agents that never get more than their creator; both use `addAgent`/`removeAgent` in `runtime/helpers.ts`, as the API does), `computer-tools.ts` (shell/files/browser, which call computerd over HTTP), `desktop-tools.ts` (opt-in whole-desktop control) and `coding-tools.ts` (`run_coding_agent`). A tool's optional `available(agent, app)` hides it from agents it doesn't apply to. MCP tools (`tools/mcp.ts`) come from `mcp.json` at the repo root (same format as Claude's `.mcp.json`) and from **connectors** added in Settings (remote servers with OAuth handled by the MCP SDK; the provider keeps tokens in the vault under `connectorSecret(name)`). Both are exposed as `mcp__<server>__<tool>` with risk `external` and are only offered to agents that list the server.

### Policy (`policy.ts`)
YAML rules (`DEFAULT_POLICY_YAML`, editable in Settings and stored in the DB) match on tool globs, agent, initiator, domain, target-label regex, field types, arg regexes (tool arguments after zod defaults are applied) and an optional CEL `when:` expression (fails closed). **The strictest match wins:** deny > handoff > ask > review > allow. If nothing matches, the risk-class default applies. Changing `DEFAULT_POLICY_YAML` only affects workspaces that never saved their own policy.

### Secrets, people and sign-in
- `vault.ts`: secrets are AES-256-GCM in the DB. Names starting `TEAMBOT_` are **reserved**: features use them for their own credentials (bridge tokens, routine passwords via `routineSecret(id)`, connector tokens via `connectorSecret(name)`), and agents can neither see nor use them (`vault.agentNames()`, `resolve(..., { forAgent: true })`).
- `auth.ts` + `api.ts`: team mode is off by default (setting `team_mode`). Then every request acts as `workspace.owner()`. With it on, the `onRequest` hook resolves the `teambot_session` cookie to `req.human`, answers 401 without one (except `/api/auth/*` and `/api/hooks/*`), refuses cross-site changes, and limits `OWNER_ONLY` routes to owners (plus an agent's `setupScript`, `computerImage`, `network` and `budget`: `checkOwnerAgentFields`). In handlers, attribute actions with `me(req)`, never `workspace.owner()`. `workspace.canSee(channel, viewerId)` keeps DMs that include a person private to their members; apply it (via `channelFor`/`channelVisible`/`runVisible`/`visibleTo` in `api.ts`) to anything new that returns messages, runs, approvals or events. A DM's members can't be changed. Agents read through `workspace.canSeeFrom(channel, agentId, run.channelId)`: in team mode, only what everyone in the run's conversation could read. Before any of that, the hook refuses requests from agent computers (`computers.isComputerAddress`).

### Agent computers (`computer/`, `computers/docker.ts`)
There is one container (`teambot-<agentId>`) plus one home volume (`teambot-home-<agentId>`) per agent. The image runs Debian with Xvfb, Fluxbox, Chromium (driven by `computerd` via playwright-core over CDP, so humans watch the same browser), and x11vnc. `computerd` is a small bearer-token HTTP API (`/shell`, `/fs/*`, `/browser/*`); `/fs/write` is text-only. The token and VNC password are derived from the master key (`vault.derive`). Browser elements are addressed by numeric refs from `browser_snapshot` (the `data-tb-ref` attribute). Changes under `computer/` only take effect after `pnpm computer:build`. A **stopped** computer built from another or an older image (an agent can set its own `computerImage`) is recreated on next use (its home volume is kept), but a running one keeps the old image until it is stopped. In host mode the ports are published to 127.0.0.1. When the server itself runs in Docker (`TEAMBOT_COMPUTER_NETWORK` set), computers are reached by container name.
Network: the entrypoint starts as root with `NET_ADMIN` only to block all output except loopback and replies, then drops to `agent` without that capability (sudo can't get it back; `docker exec` processes still have it). The server's `FIREWALL` (privileged exec, via `syncNetwork` on every `ready()` after a start) then opens it: to the egress proxy only (allowlist), or to everything except the TeamBot host (`host.docker.internal` and the server's own addresses), because the API acts as the owner with sign-in off and Docker Desktop forwards `host.docker.internal` to the host's 127.0.0.1. A failure to apply rules fails the computer, in both modes.

## Testing approach

Connector tests run a local fake OAuth + MCP server (`test/connectors.test.ts`); team-mode tests keep a cookie per person around `server.inject` (`test/team.test.ts`). `test/helpers.ts` → `testApp()` builds an App with an in-memory DB, `ScriptedProvider` (`models.script('test/<agentname>', [say(...), callTool(...)])`, queued replies per model id, defaulting to `[silent]`; the reviewer is `test/reviewer`) and `FakeComputers` (fake page elements and an echo shell whose commands containing `exit 1` fail, recording every call, stop and image). `addAgent(app, 'Writer')` gives the agent model `test/writer`. Drive scenarios by posting messages via `app.workspace.postMessage(...)`, then `await app.runtime.idle()`, and stop the runtime in `afterEach`. HTTP behaviour is tested with `buildServer(app)` and `server.inject(...)`. Time-based sweeps take a time argument (`proactive.sweep(at)`, `lifecycle.sweep(at)`). Create `app.cfg.sharedDir` yourself in tests that touch `/shared`.

## Gotchas

- Keep heavy or optional dependencies lazily imported (the MCP SDK, imapflow, mailparser and ical.js are loaded with `await import(...)`; cel-js is small and imported normally). The `.claude/launch.json` preview servers freeze completely whenever they import the MCP SDK — eagerly at startup, or lazily when a connector is added or saved connectors reconnect at boot — while the same command started from a shell works. Check connector UI against a server started from the shell on another port with a scratch `TEAMBOT_DATA_DIR`, and don't leave a connector saved in the verify data folder.
- zustand v5: a selector that returns a new array or object on every call (`useStore((s) => s.x.filter(...))`) loops forever and blanks the app (React error #185). Select stable values, wrap the selector in `useShallow`, or derive with `useMemo`.
- The shared `Modal` uses `dialog.showModal()`, which focuses the close button. Mark a dialog's first field with `data-autofocus`, not React's `autoFocus`.
- zod `.partial()` keeps `.default()` values, so a PATCH schema built from a create schema silently resets fields. Build PATCH schemas from fields without defaults (see `agentFields`/`scheduleFields` in `api.ts`).
- On this Windows/OneDrive setup, Docker Desktop isn't always running, and the first `tsx` import is slow (~7–10 s).
- The server binds 127.0.0.1 and controls the Docker socket. With team mode off there is no auth and every human action is the owner's; with it on, see "Secrets, people and sign-in" above. Bridges, routines without a channel and the Telegram/Slack pairing still belong to the owner.
