# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

TeamBot is a self-hosted workspace (for one person, or a small team with sign-in turned on) where named AI agents (any OpenRouter model per agent) each get their own isolated Docker "computer" and collaborate with humans and each other in chats and group chats. There is no task board: an agent shows its plan as a progress checklist on its run, and hands work to a teammate by message. Every tool call passes a policy gate. P0 and P1 are complete; the roadmap (P2 next) and the P1 progress table live in `docs/FEATURE_MAP.md` (check its priorities before proposing new features).

## Commands

pnpm 10 monorepo, Node ≥ 22.13 (the server uses the built-in `node:sqlite`). Docker is needed only for real agent computers.

```bash
pnpm install
pnpm dev                 # server :8787 (tsx watch) + Vite :5173 with /api proxied; open :5173
pnpm build               # builds apps/web only; the server has no build step (runs TS via tsx)
pnpm start               # server on :8787, serves apps/web/dist if it exists
pnpm test                # vitest in apps/server (the only package with tests)
pnpm typecheck           # tsc --noEmit in server, web and computerd
pnpm computer:build      # docker build of the agent computer image (computer/)

# single test file / single test
pnpm --filter @teambot/server exec vitest run test/policy.test.ts
pnpm --filter @teambot/server exec vitest run test/runtime.test.ts -t "answers a DM"

# end-to-end against a real container (needs Docker + the built image)
TEAMBOT_DOCKER_TESTS=1 pnpm --filter @teambot/server test
```

There is no linter or formatter configured. Config comes from env vars, and `.env` at the repo root is loaded by `apps/server/src/config.ts`, which walks up to the folder containing `pnpm-workspace.yaml`; variables already set in the environment win over `.env`. See `.env.example`. `OPENROUTER_API_KEY` is required for agents to think (or set `TEAMBOT_OFFLINE_MODELS=1` for a free echo model when trying the UI). Runtime data lives in `./data`: the SQLite DB, `master.key`, `shared/`, `skills/<name>/SKILL.md`, `memory/` (`team.md`, `agents/<Name>.md`) and `recordings/<id>/` (stills of skill drafts).

`.claude/launch.json` has a `teambot-verify` configuration: a server on :8788 with its own data folder and offline models, serving `apps/web/dist` (run `pnpm build` after UI changes). Use it to check UI work without touching the real workspace or spending credits.

## Architecture

Packages: `apps/server` (Fastify + runtime), `apps/web` (React 19 + Vite + zustand + wouter), `packages/shared` (domain types, consumed as raw TS source with no build), `computer/` (agent container image + `computerd`).

### Server composition (`apps/server/src/app.ts`)
`createApp(cfg, overrides)` wires everything into one `App` object that is passed to every service (`store, bus, vault, policy, models, computers, mcp, tools, workspace, runtime, handoffs, cron, budgets, skills, memory, lifecycle, telegram, slack, telemetry, egress, snapshots, triggers, auth, pages, comments, components`). Tests swap `models`, `computers` and the outside APIs (Telegram, Slack, mail, calendar, OTLP) for fakes through `overrides`. Server imports use NodeNext ESM, so relative imports need the `.js` extension. Web uses Bundler resolution, so it doesn't.

### State, events and the UI
- `store.ts`: all persistence on synchronous `node:sqlite`. Schema changes are **appended** to the `MIGRATIONS` array (versioned by index in `meta.schema_version`). Never edit an existing entry. Node 22's SQLite has no FTS5, so search uses `LIKE`.
- `bus.ts`: `bus.emit(type, scope, data)` appends to the `events` table, which serves as both the **audit log** and every run's work log (the notes in chats and the panel's full log), then fans out to WebSocket clients on `/api/ws`. Spend is computed from events too: every model call emits one of `COST_EVENTS` (`runtime/budget.ts`) with `costUsd`/`inputTokens`/`outputTokens`, so a new kind of model call must emit cost the same way or budgets won't see it (`recording.drafted` has no agent in its scope, so it counts toward the workspace only).
- Web: `apps/web/src/store.ts` loads `/api/bootstrap` once, then applies live events by `type` (e.g. `agent.*` events carrying `data.agent` are upserted). A server-side state change only shows up live if it emits an event the web store handles. The channel view holds top-level messages (with `replyCount`); thread replies live in `threads[rootId]`. The UI is a chat app (see `design.md`): the sidebar lists conversations from `lastMessages`, a chat shows work notes from `runSummaries` (`/api/runs?ids=`), and the right panel's pages (`panel.view`) are scoped to the path they were opened on (`panel.at`).

### Work routing (`workspace.ts`)
Posting a message is how work gets routed. `@mentions`, DMs to an agent, human replies in a thread an agent is part of, a channel's `leadAgentId` (for human messages that mention nobody), routines (`runtime/cron.ts` fires them; triggers are cron, webhook, email/calendar polled by `runtime/triggers.ts`, and Slack channel messages from `bridges/slack.ts`) all add rows to the agent's **inbox**. A DM is between the two members it was opened with, forever: posting joins only group channels, and in a DM with an agent only that agent gets the message (a mention routes into a DM only between people). The web finds a person's chat with an agent by exactly those two members, so a DM that gained one would vanish from the UI. Telegram and Slack DMs come in through `bridges/` as the owner's messages. @mentions in **page comments** (`comments.ts`) route the same way, but the inbox item, and the run it starts, carry `commentThreadId` (the thread's root comment) instead of a channel: the run has `channelId: null`, its final reply (and any runtime notice) is posted in the thread by `say()`, `ask_agent` answers come back there (`originCommentThreadId`), and a person replying in a thread continues with the agents already in it. Agents hand each other work with `ask_agent` (`runtime/handoffs.ts`; `send_dm` is for people) or an @mention in a group chat; there are no temporary helpers or sub-agents (migration 16 removed the last of them). `ask_agent` posts a structured request (task, context, constraints, what a good answer looks like) in the two agents' DM and records a **handoff**. The asked agent's next reply in that DM is the answer: `route()` hands it to `handoffs.answer` instead of waking the asker in the DM, and it goes back to the asking run's conversation and thread, all of that run's answers in one inbox item once none is open. The handoff keeps the answering message (`answerId`), which the asking conversation shows as "Message from …". After answering, the runtime gives the asked agent one more turn (`headsUpRequest`) whose reply is posted in its DM with the person the request was for (`handoffs.headsUp`, following agents that asked on someone's behalf; none for group chats). `handoffs.settle` (called when a run completes, fails or is cancelled) reports requests that ended unanswered back the same way, unless the asked agent is itself waiting on a teammate for that conversation; a cancelled or failed asking run cancels its open requests. A run may hand work to `TEAMBOT_MAX_HANDOFFS_PER_RUN` teammates (ask_agent plus agents @mentioned in group chats). Each item carries a `depth` (agent-to-agent hops since a human), an `initiator` (human/agent/schedule/event), an optional `threadId` and a `readOnly` flag. If depth exceeds `TEAMBOT_MAX_AGENT_DEPTH`, the loop guard drops the item. Attachments are paths in `/shared` (`shared-files.ts`), validated on the server where they really lead: agents can create links in `/shared`, so reads go through `openSharedFile`/`realSharedPath` and uploads never follow a link. An agent's message also carries the existing `/shared` files its text names (`sharedFilesIn`), so a reply like "Saved /shared/report.md" arrives with the file attached, and the agent's Library (its messages' attachments) lists it. `postMessage` strips null bytes: SQLite keeps text only up to the first one.

### Runtime (`runtime/runtime.ts`)
- **Scheduling:** `poke()` and a 3 s timer dispatch at most one active run per agent, capped by `maxConcurrentRuns`. An agent over budget (`runtime/budget.ts`) is skipped; its work waits. A run turns inbox items into a user message. Inbox items for the same conversation (channel, thread or page comment thread, and read-only flag) that arrive mid-run are folded into the same run; anything else waits for its own run (`belongsTo`), so a DM is never answered in a channel. Consuming input, saving the transcript and updating the run happen in one `store.tx`.
- **Each step:** the budget is checked (over budget → the run goes back to `queued` with a message), the system prompt is rebuilt from scratch (`runtime/prompt.ts`: roster, skills, memory, secret names, and the agent's last jobs in other conversations, filtered by `canSeeFrom`), then the model is called and the transcript is persisted. Long transcripts are summarized by the utility model (`runtime/compaction.ts`). A final assistant message with no tool calls is posted to the run's channel (and thread) automatically. The reply `[silent]` suppresses it. An empty one (some models end a turn with reasoning only) gets one `EMPTY_REPLY_NUDGE` asking for the reply, then a note in the chat, so a run never finishes in silence. Null bytes never belong in model output (`garbled`): a garbled reply is not posted (`GARBLED_REPLY_NUDGE` asks again), tool arguments holding one are refused before anything runs, and two garbled turns in a row fail the run with an error that says to pick another model. A reply that stopped at the output limit (`finishReason: 'length'`) is marked `cutOff` in the transcript (stripped on the way to the model), so its broken tool call is explained as cut off rather than as invalid JSON. At `TEAMBOT_MAX_STEPS_PER_RUN` model calls the run completes without a final reply; the agent's next run in that conversation (same channel, thread and read-only flag) that a message starts takes over that transcript and checklist behind a `RESUME_NOTE` (`cutShort`), so "continue" carries on instead of starting over. Read-only runs are offered only tools for which `usableReadOnly(tool)` holds (risk `read`, or `readOnlyOk: true`; never set it on a tool that changes memory or agents; `update_progress` has it because the checklist belongs to the run). Messages a read-only run sends route work to other agents as read-only too.
- **Durability:** state lives in the DB (transcript + `tool.started`/`tool.finished` events), not in memory. On restart, `recover()` re-queues `running` runs. A tool that started gets an explicit result instead of being re-run: "Interrupted" if it never finished, or the `tool.finished` preview if it finished before its result reached the transcript. It is **never silently re-run**. Pausing or cancelling a run also calls `computers.cancelWork` (computerd's `/cancel`) and waits for it, so no command keeps running on the computer. Keep this invariant when touching the loop.
- **Gateway (`handleCall`):** zod-validate args → collect `facts` (for browser tools, the target element label, field type and domain, fetched from the computer) → `policy.evaluate` → for `review`, ask the reviewer model (`runtime/reviewer.ts`; any failure means `ask`) → for `ask`/`handoff`, create an Approval and return `waiting_approval`/`waiting_human` (the run resumes when `resolveApproval` re-queues it) → `vault.resolve` substitutes `{{secret:NAME}}` → execute → `vault.redact` the output → truncate → wrap in `<untrusted_content>` if the tool is `untrusted` → emit events. Secret values never enter prompts or transcripts (screenshots from an action that used a secret are withheld; values under 4 characters are refused), but an agent with a shell can still deliberately reveal one it may use.
- Pause, cancel, takeover and hand-back work by aborting the run's `AbortController` with a reason.
- **Computers over time** (`runtime/lifecycle.ts`): tools get their computer through `lifecycle.ready(agent)`, which starts it on the agent's image and runs its setup script once per script version (marker in `~/.teambot/setup.sha`). A sweep stops computers idle for `TEAMBOT_COMPUTER_IDLE_MINUTES`, never while the agent has an active run, a takeover or a live viewer.

### Tools (`tools/`)
Tools are `defineTool({ name, description, schema (zod), risk, untrusted?, facts?, summarize?, execute })`. `risk` (`internal | read | write | external`) selects the policy default; `untrusted: true` tags the output as outside content. Built-ins are `workspace-tools.ts` (messages with attachments, `update_progress`, which saves the run's checklist in `runs.progress` and emits `run.progress` with the run, `ask_for_approval`/takeover requests via `FORCED_APPROVAL_TOOLS`), `knowledge-tools.ts` (`use_skill`, `remember`/`forget`, `search_history`), `agent-tools.ts` (`create_agent`, for permanent agents that never get more than their creator; it uses `addAgent`/`removeAgent` in `runtime/agents.ts`, as the API does), `routine-tools.ts` (`create_routine` for time-based routines for itself or a teammate, reviewed by default, at most every `MIN_ROUTINE_MINUTES` and never from a routine's own run; `list_routines`; `stop_routine`, which pauses with `pause: true` and otherwise removes a routine an agent set up but only pauses one a person made; `resume_routine`, not from a routine's own run; who set one up is the `schedule.created` event's actor), `computer-tools.ts` (shell/files/browser, which call computerd over HTTP), `desktop-tools.ts` (opt-in whole-desktop control) and `coding-tools.ts` (`run_coding_agent`). A tool's optional `available(agent, app)` hides it from agents it doesn't apply to, and `returnsImages` (e.g. `browser_screenshot`, for charts and tables drawn as images) hides it from models OpenRouter lists as text-only (`seesImages` in `runtime/vision.ts`). MCP tools (`tools/mcp.ts`) come from `mcp.json` at the repo root (same format as Claude's `.mcp.json`) and from **connectors** added under Connect apps, from the catalog in `apps/web/src/lib/catalog.ts` (vendors' own servers, checked to allow TeamBot's sign-in; never fill it from open registry search) or by URL. A connector signs in with OAuth handled by the MCP SDK (the provider keeps tokens in the vault under `connectorSecret(name)`) or, when `connector.token` is set, sends a pasted token in that header (kept as its own reserved secret, `connectorTokenSecret(name)`, so it is redacted like any secret). Both are exposed as `mcp__<server>__<tool>` with risk `external` and are only offered to agents that list the server.

### Pages and generative UI (`pages.ts`, `components.ts`)
- **Pages** are workspace-wide Markdown documents (like `/shared`). `Pages.update(id, patch, expectedRevision, by)` writes only over the revision the editor started from (`UPDATE … WHERE revision = :expected`); otherwise it throws `PageConflict` with the current page (the API answers 409 with `{ error, page }`). A save that changes nothing is never a conflict. `page.*` events carry a summary without content and no run or channel scope, so everyone gets them; the open editor refetches. Agents use `tools/page-tools.ts`: `edit_page` requires `expected_revision` and takes find-and-replace `edits` (each must match once) or a whole `content`. `propose_page` is in `FORCED_APPROVAL_TOOLS` (review before saving); it saves with `source = { runId, callId }` (`ToolContext.callId`), which a unique index makes idempotent. The web editor's autosave is `apps/web/src/lib/autosave.ts`.
- **Comments** (`comments.ts`, migration 20): threads on a page, each a root comment (with an `anchor`: the quoted passage, its offset and the revision) plus replies. `locateAnchor` (shared, used by server and web) finds the passage again in the current text, nearest the old offset; null means outdated, and the thread is kept. A new anchor must be in the page as saved (409 otherwise), so the editor flushes before commenting. `page.comment.created/updated/deleted` events carry `openComments` and no run or channel scope; `PageSummary.openComments` counts unresolved threads. Anyone resolves; only the author or an owner deletes (`CommentForbidden`, 403). Agent tools: `list_page_comments` (untrusted), `comment_on_page` (`readOnlyOk`, like messages; its @mentions count toward the run's handoff limit) and `resolve_comment`.
- **Generative UI**: a message may carry a `widget` (a copy of the html/css/js and the args, so old chats don't change). `show_ui` (`tools/ui-tools.ts`, off with `TEAMBOT_GENERATIVE_UI=0`) draws one the agent writes; each published component is a tool `ui_<name>` built by `ComponentLibrary.toolsForAgents()` (args validated with `z.fromJSONSchema` of its schema; rebuilt per published revision). Drafts reach nobody: publishing (owner-only in team mode, `/api/components` is in `OWNER_ONLY`) copies the draft into `published`; withdrawing keeps it. An agent's `draft_component` can't overwrite a draft a person saved last. `showWidget` posts with `route: false`, so a picture never wakes anyone or answers an `ask_agent`.
- **The sandbox** (`apps/web/src/components/WidgetFrame.tsx`): `sandbox="allow-scripts"` (opaque origin) plus a meta CSP with `connect-src 'none'` and scripts/styles only from three CDNs; the theme goes in as `--tb-*` variables; the frame posts back only its size, script errors and `teambot.reply` text (which lands in the composer via `composerDraft`, consumed once). The API refuses non-GET requests with `Origin: null`. Never add `allow-same-origin`.
- **Tool cards** (`apps/web/src/components/ToolCard.tsx`) are built from a run's `tool.checked`/`tool.started`/`tool.finished`/`approval.resolved` events; `WorkLog.tsx` shows them under the live line and in the finished note.
- **File previews** (`apps/web/src/components/FileView.tsx`, kinds in `lib/files.ts`): a file card in a message opens the file beside the chat (`panel.view` `{ kind: 'file' }`, `panel/FilePanel.tsx`, a wider panel you can drag) and elsewhere in a dialog (`openFile`); a new agent message with files opens its first one if the panel isn't busy. Markdown, code (highlight.js, lazily loaded), CSV and notebooks render in the app; images, audio and video use the browser; web pages run in the widget sandbox with its policy put first (`pageDocument`); Word, Excel, PowerPoint, PDF and Mermaid are drawn in that sandbox by viewer libraries from the allowed CDNs (`VIEWERS`, pinned), which get the bytes by `postMessage` after the frame says it is ready. `/api/shared/file` serves HTML and SVG as text, with an etag: previews send HEAD on every `tool.finished` and reload only when it changed (`useFilesVersion`).

### Learning by demonstration (`recordings.ts`, `computer/computerd/src/recorder.ts`)
A person records a browser task on an agent's computer and the utility model drafts a SKILL.md from it. `Recordings.begin` takes the computer from the agent (`runtime.takeover`, so the agent's actions are never recorded as the person's) and calls computerd's `/record/start`: a Playwright binding (`__teambotRecord`) carries each frame's trusted clicks, typed values, choices, ticks, files and keys, and computerd announces pages on `framenavigated`. `collect()` (every `POLL_MS`, or when a test calls it) drains `/record/events`, validates each action with zod, replaces stored secrets' values with placeholders (`vault.redact`, names in `secrets`), never keeps a value for a `sensitive` or password field, and saves a still from `/record/screenshot` (every field masked by Playwright) unless a secret was typed on that page (`pageOf`: origin + path). `end()` (Stop, hand-back via the bus, a stopped computer, `MAX_RECORDING_MS`/`MAX_ACTIONS`) drains `/record/stop` and starts `draft()`, which wraps the log in `<untrusted_content>`, adds a few stills when the utility model sees images, and normalizes the reply with `finishDraft` so it always parses. Drafts live in the `recordings` table and `data/recordings/<id>/`, never in `data/skills`, so no agent can load one until a person saves it (`save()`: 409 on a name clash unless `overwrite`; deletes the draft and its stills). In team mode `visibleTo` keeps a recording to its maker and owners, and `recordingNewsVisible` in `api.ts` does the same for `recording.*` events. Changes to the recorder need `pnpm computer:build`; computerd has no tests, so check it against a real Chromium (it must be compiled with tsc: tsx's name helpers break functions sent to the page).

### Policy (`policy.ts`)
YAML rules (`DEFAULT_POLICY_YAML`, editable in Settings and stored in the DB) match on tool globs, agent, initiator, domain, target-label regex, field types, arg regexes (tool arguments after zod defaults are applied) and an optional CEL `when:` expression (fails closed). **The strictest match wins:** deny > handoff > ask > review > allow. If nothing matches, the risk-class default applies. Changing `DEFAULT_POLICY_YAML` only affects workspaces that never saved their own policy.

### Secrets, people and sign-in
- `vault.ts`: secrets are AES-256-GCM in the DB. Names starting `TEAMBOT_` are **reserved**: features use them for their own credentials (bridge tokens, routine passwords via `routineSecret(id)`, connector sign-ins via `connectorSecret(name)` and `connectorTokenSecret(name)`), and agents can neither see nor use them (`vault.agentNames()`, `resolve(..., { forAgent: true })`).
- `auth.ts` + `api.ts`: team mode is off by default (setting `team_mode`). Then every request acts as `workspace.owner()`. With it on, the `onRequest` hook resolves the `teambot_session` cookie to `req.human`, answers 401 without one (except `/api/auth/*` and `/api/hooks/*`), refuses cross-site changes, and limits `OWNER_ONLY` routes to owners (plus an agent's `setupScript`, `computerImage`, `network` and `budget`: `checkOwnerAgentFields`). In handlers, attribute actions with `me(req)`, never `workspace.owner()`. `workspace.canSee(channel, viewerId)` keeps DMs that include a person private to their members; apply it (via `channelFor`/`channelVisible`/`runVisible`/`visibleTo` in `api.ts`) to anything new that returns messages, runs, approvals or events. A DM's members can't be changed. Agents read through `workspace.canSeeFrom(channel, agentId, run.channelId)`: in team mode, only what everyone in the run's conversation could read. Before any of that, the hook refuses requests from agent computers (`computers.isComputerAddress`).

### Agent computers (`computer/`, `computers/docker.ts`)
There is one container (`teambot-<agentId>`) plus one home volume (`teambot-home-<agentId>`) per agent. The image runs Debian with Xvfb, Fluxbox, Chromium (driven by `computerd` via playwright-core over CDP, so humans watch the same browser), and x11vnc. `computerd` is a small bearer-token HTTP API (`/shell`, `/fs/*`, `/browser/*`); `/fs/write` is text-only, so agents make binary files (Word, Excel, PowerPoint, PDF, charts) with Python: the image has python-docx, openpyxl, xlsxwriter, python-pptx, reportlab, pypdf, matplotlib, pandas and pandoc (build arg `DOCUMENT_TOOLS=0` leaves them out). The token and VNC password are derived from the master key (`vault.derive`). Browser elements are addressed by numeric refs from `browser_snapshot` (the `data-tb-ref` attribute). Changes under `computer/` only take effect after `pnpm computer:build`. A **stopped** computer built from another or an older image (an agent can set its own `computerImage`) is recreated on next use (its home volume is kept), but a running one keeps the old image until it is stopped. In host mode the ports are published to 127.0.0.1. When the server itself runs in Docker (`TEAMBOT_COMPUTER_NETWORK` set), computers are reached by container name.
Network: the entrypoint starts as root with `NET_ADMIN` only to block all output except loopback and replies, then drops to `agent` without that capability (sudo can't get it back; `docker exec` processes still have it). The server's `FIREWALL` (privileged exec, via `syncNetwork` on every `ready()` after a start) then opens it: to the egress proxy only (allowlist), or to everything except the TeamBot host (`host.docker.internal` and the server's own addresses), because the API acts as the owner with sign-in off and Docker Desktop forwards `host.docker.internal` to the host's 127.0.0.1. A failure to apply rules fails the computer, in both modes.

## Testing approach

Connector tests run a local fake OAuth + MCP server (`test/connectors.test.ts`); team-mode tests keep a cookie per person around `server.inject` (`test/team.test.ts`). `test/helpers.ts` → `testApp()` builds an App with an in-memory DB, `ScriptedProvider` (`models.script('test/<agentname>', [say(...), callTool(...)])`, queued replies per model id, defaulting to `[silent]`; the reviewer is `test/reviewer`) and `FakeComputers` (fake page elements and an echo shell whose commands containing `exit 1` fail, recording every call, stop and image; `recorder[agentId].events` is what a person did for `/record/events`, `stillUrl` the page a still shows, `off` computers that report stopped). `testApp()` collects recordings only when a test calls `app.recordings.collect(id)`. `addAgent(app, 'Writer')` gives the agent model `test/writer`. Drive scenarios by posting messages via `app.workspace.postMessage(...)`, then `await app.runtime.idle()`, and stop the runtime in `afterEach`. HTTP behaviour is tested with `buildServer(app)` and `server.inject(...)`. Time-based sweeps take a time argument (`lifecycle.sweep(at)`). Create `app.cfg.sharedDir` yourself in tests that touch `/shared`.

## Gotchas

- Keep heavy or optional dependencies lazily imported (the MCP SDK, imapflow, mailparser and ical.js are loaded with `await import(...)`; cel-js is small and imported normally). The `.claude/launch.json` preview servers freeze completely whenever they import the MCP SDK — eagerly at startup, or lazily when a connector is added or saved connectors reconnect at boot — while the same command started from a shell works. Check connector UI against a server started from the shell on another port with a scratch `TEAMBOT_DATA_DIR`, and don't leave a connector saved in the verify data folder.
- zustand v5: a selector that returns a new array or object on every call (`useStore((s) => s.x.filter(...))`) loops forever and blanks the app (React error #185). Select stable values, wrap the selector in `useShallow`, or derive with `useMemo`.
- Widget documents are built as strings: JSON inside `<script>` must escape `<` (as `\u003c`) and source text must not close its element (`</script`, `</style`). Tool calls that write such escapes through a shell heredoc have mangled backslashes before; check the bytes.
- Give effects braces (`useEffect(() => { el.scrollIntoView(); })`): current Chromium returns a promise from `scrollIntoView`, and an arrow that returns it makes React call it as the cleanup, which blanks the app.
- The shared `Modal` uses `dialog.showModal()`, which focuses the close button. Mark a dialog's first field with `data-autofocus`, not React's `autoFocus`.
- zod `.partial()` keeps `.default()` values, so a PATCH schema built from a create schema silently resets fields. Build PATCH schemas from fields without defaults (see `agentFields`/`scheduleFields` in `api.ts`).
- On this Windows/OneDrive setup, Docker Desktop isn't always running, and the first `tsx` import is slow (~7–10 s).
- The server binds 127.0.0.1 and controls the Docker socket. With team mode off there is no auth and every human action is the owner's; with it on, see "Secrets, people and sign-in" above. Bridges, routines without a channel and the Telegram/Slack pairing still belong to the owner.
